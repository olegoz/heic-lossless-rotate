# Release 1.6.0 (2026-09-19) — detailed changes

This release adds tool-version tracking to the provenance record, a
post-rotate reversibility self-check, and a leaner provenance record
format — plus the test suite and documentation changes that came with
each.

## Tool-version tracking (`TVER`)

The provenance record now stores which `heic_rotate.py` version most
recently updated the file — 3 fixed bytes (major/minor/patch), written
fresh by `rotate` on every edit. `info` now shows it:

```
Rotated with heic_rotate.py v1.6.0, provenance format v2.
```

This is a "who last updated this file" marker, not a history of every
version that has ever touched it — each edit overwrites it with the
version currently running. `reverse` verifies reversibility too, but
never writes this marker, since reversing isn't an update of its own.

Because it's a new field, an already-edited file from an older tool
version won't have it. The provenance-box update logic was generalized
to handle this: inserting a brand-new record, updating an existing
same-size record, and growing an existing record to fit a new field are
now all one code path, rather than two separate ones as before.

## Post-rotate reversibility self-check

Before writing anything, `rotate` now reverses its own freshly-produced
output in memory and confirms the result matches the recorded original
exactly. If it doesn't, `rotate` refuses to write the output file at
all, rather than producing a file that later turns out not to be
reversible. This runs unconditionally, including under `--dry-run`, and
is a stronger guarantee than checking the CRC at `reverse` time alone:
it verifies each edit's own reversibility while the true original bytes
are still in hand.

## Leaner provenance record format

Previously, every edit saved a full copy of the file's `iprp` box (the
container for `irot` and any other item properties) as part of making
itself reversible — even though `irot` is the only property this tool
ever reads or writes. A file with other properties in `iprp` (an
embedded ICC colour profile, for example) paid for a copy of those too,
for no functional reason.

The record now saves only `irot`'s own pristine state:
- if `irot` already existed: its original byte value
- if it didn't: a marker, plus `ipma`'s original flags (needed only to
  correctly restore `ipma` if inserting `irot` had required widening its
  index encoding)

Measured saving on a small test file with one unrelated property: 173 →
128 bytes (~26%) for the provenance record. The saving scales with how
much unrelated data a real file's `iprp` happens to carry.

`reverse` supports both formats directly — it doesn't require an old
file to be upgraded before it can be reversed. `rotate` migrates an old
record to the new format automatically the next time it edits that
file, which means **`rotate 0` can now be used purely to shrink an old
file's provenance record** (or add a field like `TVER`) without
changing how the image displays.

One behavior note for `reverse --ignore-tamper-check`: the previous
format's full-`iprp` copy meant that flag happened to also recover
tampering anywhere in `iprp`, as a side effect of overwriting all of it
regardless of content. The new format only restores `irot` itself, so
that incidental side effect is gone — tampering elsewhere in `iprp` is
still always detected (the final whole-file CRC check is unconditional
and unaffected by this flag), it just can no longer be silently
papered over by it. Not a limitation of normal use; only relevant if
something has already gone wrong.

## `rotate`'s default output filename now recognizes `_restored` inputs

If no output path is given, `rotate` used to always write to
`<input>_rotated.heic`. Now, if `<input>` (stem, minus extension) ends
with `_restored` — i.e. it looks like `reverse`'s own default output —
the default strips that suffix instead of piling `_rotated` on top of
it:

```
photo_restored.heic → photo.heic
```

Any other input name is unaffected (`<input>_rotated.heic` as before),
an explicit output argument always overrides either default, and the
existing refuse-to-overwrite-unless-`-f` behavior applies identically
either way.

## Documentation

- The script's module docstring now leads with `USAGE` right after the
  one-line summary, matching the README's practical-first structure —
  previously it led with internal design notes.
- `README.md` updated to describe the above changes, including a
  `rotate 0` example for bringing an old file's metadata up to date,
  and the new `_restored`-stripping default filename behavior.

## Tests

Suite grew from 29 to 42 tests:
- Coverage for `TVER`, the record-growth migration path, and the
  post-rotate self-check (including a mocked-failure case proving
  `rotate` writes nothing if the check fails).
- Coverage for the new provenance format: new records use it, `reverse`
  still supports the old format directly, and old records migrate
  correctly on the next edit.
- An existing tamper-recovery test had assumed `reverse` blindly
  overwrites all of `iprp` regardless of content — true only as a side
  effect of the old format, not a designed guarantee. Replaced with
  tests that pin down the new, narrower recovery boundary precisely.
- `TestRealFiles`'s `rotated/`/`testdata/` directories can now be
  symlinks to an external disk — the directory-clearing step no longer
  uses `shutil.rmtree` (which refuses to run on a symlink) and instead
  clears the directory's contents in place.
