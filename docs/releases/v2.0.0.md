# Release 2.0.0 (2026-11-09): detailed changes

This release fixes how two common kinds of phone photo were rotated:
mirrored photos (for example iPhone front-camera shots) and HDR photos
that carry a gain map (recent iPhones and Samsung Galaxy phones). It
also introduces provenance record format 3, which every edit now
writes, and gives each kind of error its own exit code instead of 10
for all of them (see
[Soft and hard errors, and new exit codes](#soft-and-hard-errors-and-new-exit-codes)).
If you rotated either kind of photo with an earlier release,
see [Repairing files rotated by earlier releases](#repairing-files-rotated-by-earlier-releases).

## Mirrored photos were rotated in the wrong direction

A HEIF image can carry a mirror property (`imir`) as well as a rotation
(`irot`), and viewers apply them in the order the file lists them.
iPhone front-camera shots list the rotation first and the mirror
second. A mirror reverses the visible direction of any rotation applied
before it, so when earlier releases added 90° to `irot`, the photo
turned 90° clockwise instead of counter-clockwise. 180° rotations
looked right only because 180° is the same in either direction.

The tool now checks the order of the primary image's properties. When
an odd number of `imir` properties follow `irot`, it changes `irot` in
the opposite direction, so the displayed image turns the way you asked.
Files that list the mirror before the rotation, or have no mirror, are
handled as before.

`info` now reports the rotation you asked for. For a file rotated by
2.0.0, that is exactly what you see on screen, mirrored or not: rotate
the original by 90° and viewers show it turned 90° counter-clockwise,
and `info` says 90. For a mirrored file it also explains why the raw
`irot` value moved the other way:

```
Rotated with heic-lossless-rotate v2.0.0, provenance format v3.
  heic-lossless-rotate has added: 90 deg
  file's 'irot' value: 90 deg originally -> 0 deg now (mirrored after rotating, so the displayed image turns the opposite way to this value)
```

For a mirrored photo rotated by 90° or 270° with an earlier release, the
screen shows the opposite turn, but `info` still reports the angle you
asked for. That is also the angle `rotate 0` re-applies when it repairs
the file, and `info` points this out for any file with older metadata:

```
Rotated with heic-lossless-rotate v1.7.1, provenance format v2.
  heic-lossless-rotate has added: 90 deg
  file's 'irot' value: 90 deg originally -> 180 deg now (mirrored after rotating, so the displayed image turns the opposite way to this value)
  metadata format is older than this release's (v3): `rotate 0` brings the file up to date, re-applying the rotation added above with this release's code
```

## Mirrored photos lost their mirroring in the Exif Orientation tag

Some readers ignore `irot`/`imir` and use the legacy Exif Orientation
tag instead. Exif has separate values for mirrored orientations
(2, 4, 5 and 7), but earlier releases always wrote an unmirrored value
(1, 3, 6 or 8). Those readers then showed the photo un-mirrored. The tag
is now derived from the file's full rotation-plus-mirror transform, so
it stays mirrored.

## HDR photos with a gain map were cropped and letterboxed

An HDR photo with a gain map (ISO 21496-1) contains, besides the main
image, a gain map and a derived "tone-mapped" image item (`tmap`) that
combines the two. HDR-capable viewers display the `tmap` item rather
than the main image. Earlier releases only knew about the main image,
which caused three problems:

- **Wrong frame shape.** The `tmap` item records its size (`ispe`) in
  the displayed orientation. That size wasn't updated, so after a 90° or
  270° turn, viewers drew the rotated photo inside a frame of the old
  shape: cropped, with blank bars along one side.
- **Rotated twice.** When the main image is unrotated, iPhones store a
  single rotation property and a single size property shared by the
  main image and the `tmap` item. Changing the shared rotation in place
  rotated the `tmap` item as well.
- **Gain map left unrotated.** When a file had no rotation property at
  all (common on Samsung phones), the one the tool inserted applied to
  the main image only, so the gain map no longer lined up with it.

For each `tmap` item derived from the main image, `rotate` now:

- sets its `ispe` to the main image's displayed size,
- keeps its own rotation at its original value, giving it a separate
  copy if it shared the main image's,
- gives it a separate copy of the size property if it was shared, so
  the main image's own size is never changed,
- rotates the gain map together with the main image.

Unrelated properties are never touched.

`info` now labels such photos:

```
Rotated with heic-lossless-rotate v1.7.1, provenance format v2.
  heic-lossless-rotate has added: 90 deg
  file's rotation: 0 deg originally -> 90 deg now
  HDR photo with a gain map ('tmap' image)
  metadata format is older than this release's (v3): `rotate 0` brings the file up to date, re-applying the rotation added above with this release's code
```

## Repairing files rotated by earlier releases

Only mirrored photos and HDR photos with a gain map, rotated by an
earlier release, need repairing (see the sections above). Other files
rotated by earlier releases are fine as they are, and 2.0.0 works with
them as usual. `info` labels both kinds of photo. If you're not sure
whether a photo is affected, repairing it anyway is harmless: for an
unaffected photo it only upgrades the metadata to format 3.

To repair a photo, run `rotate 0` on it with 2.0.0. That restores the
original in memory, checks it against the original file's checksum
stored in the record, then rotates it with 2.0.0 by the angle you asked
the earlier release for (see [How `rotate` handles older records](#how-rotate-handles-older-records)).
`rotate N` does the same, adding N on top.

The angle you asked the earlier release for isn't necessarily what it
showed you. For a mirrored photo rotated by 90° or 270°, the
earlier release turned it the wrong way on screen, so don't pick N by
what the screen shows now. Run `rotate 0`, look at the result, and if
it's not the way you want it, rotate it again by the difference.

2.0.0 reads the records written by every earlier release, but doesn't
work around their bugs. If a bug left a record 2.0.0 can't restore the
original from, `rotate` writes nothing, and its error names the release
that wrote the record, to recover the original with, and the angle to
rotate it by afterwards with 2.0.0.

If you'd rather start from the original, `reverse` the rotated file
instead, then rotate the restored file with 2.0.0 by the angle you
want. `reverse` makes the same checksum check, and also names the
release to use if it can't restore the original.

`rotate 0` on files from earlier releases was tested against the real
1.7.1 code on some real photos from iPhones and Samsung phones,
including chains of several 1.7.1 edits followed by `rotate 0`, `90`
or `270`. Each time, the result was byte-identical to rotating the
original by the same total angle with 2.0.0.

## Provenance record format 3

The provenance record is what lets `reverse` restore the exact original
file. Format 2 stored only the original `irot` byte, which was enough
while `irot` was the only property the tool changed. Fixing gain-map
photos means changing other properties and associations too, so the
record now stores only what actually changed in the item-property box
(`iprp`):

- **`OIPD`:** the original association list of each item whose
  associations in `ipma` changed (just an 8-byte header when none did).
  Usually that is no item, or only the main image when a rotation
  property had to be inserted. For a gain-map photo it can also be the
  `tmap` item or the gain map.
- **`OIPC`:** the original bytes of each existing `ipco` property that
  was changed in place, such as the rotation value or the `tmap`
  item's size. New properties are only ever appended to `ipco`, so
  `reverse` trims `ipco` back to its original length and puts these
  bytes back.
- **`OIPM`:** a full copy of the original `ipma` box. It is written
  instead of `OIPD` only as a fallback, if `OIPD` can't reproduce the
  original byte for byte. None of the real photos tested needed it.
- **`REQT`:** what you have asked the tool to do to the displayed image
  since the original, in total, as one byte: the rotation, plus a
  mirror flag reserved for a future release (one flag covers both
  directions, since a vertical flip is a horizontal flip plus 180°).
  Earlier formats didn't store this; it had to be worked out from the
  `irot` values, which only works while rotation is the only change.
  Storing it means a later release can add mirroring without a new
  format, and can always replay a format 3 record by what was asked
  for, whatever the release that wrote it actually did to `irot` and
  `imir`. Every edit also checks that it changes the displayed image by
  exactly what was requested, and writes nothing if it doesn't. `info`
  reads its "has added" line from `REQT`.

Every edit writes format 3, including on files without a gain map, so
there is one current format rather than two. Records are slightly
larger than format 2, and still far smaller than format 1's full copy
of `iprp`:

| Real photos tested | Format 2 record | Format 3 record (rotate 90) |
|---|---|---|
| Samsung, HDR | 764–774 bytes | 823–837 bytes |
| iPhone, HDR | 940–1,772 bytes | 999–1,845 bytes |

Most of each record is the original `iloc` box, which both formats
store.

**Compatibility:**

- `reverse` still restores format 1 and format 2 records directly.
- `rotate`, including `rotate 0`, replaces a format 1 or 2 record by
  starting again from the original. See below.
- Releases before 2.0.0 refuse to `reverse` a format 3 record rather
  than guessing. Once 2.0.0 has edited a file, reverse it with 2.0.0 or
  later.
- So that a later release can extend format 3 without a new format
  number, `rotate`, `reverse` and `info` all refuse a record from a
  later release that records mirroring or contains entries 2.0.0
  doesn't know, with hard error 54 (soft error 20 for unknown entries in `info` and
  `reverse`, which `--proceed-unsafe` can override) and an error naming
  the release that
  last updated the file and saying to update. Earlier releases'
  `info` and `reverse` ignored unknown entries, and `rotate` silently
  dropped them, which could lose what the later release needs to
  reverse its edit. `--proceed-unsafe` (below) makes `reverse` and
  `info` ignore unknown entries instead; nothing overrides the
  mirroring check.
- `-V` now reports format 3, and lists formats 1, 2 and 3 as
  compatible (it used to call them the formats "supported by
  reverse"; `rotate` and `info` accept them too).
- Metadata in a format newer than the running release is refused by
  `rotate`, `reverse` and `info` alike, with hard error 54 and an error
  saying to update heic-lossless-rotate, e.g.:

  ```
  ERROR Hard 54: this file was last updated by heic-lossless-rotate 2.1.0 (this is 2.0.0): its heic-lossless-rotate metadata is format v4, newer than this release supports (v3). Update heic-lossless-rotate to rotate, reverse or inspect it
  ```

  Only the record's entry layout and the version of the release that
  last updated the file are read from it; every format, now and in the
  future, keeps those two the same so that this always works. Nothing
  else in it is interpreted. Previously `info` tried to report what it
  could from such a record. That could be wrong, and it also labelled a
  corrupt record as "newer". A corrupt record is now an error (exit
  code 55) for `info` too.

## Soft and hard errors, and new exit codes

Errors used to exit with 10, whatever went wrong, with an `error:`
message. Each kind of error now has its own exit code, all 20 or above,
so none can be mistaken for an `info` result (0–4), and errors come in
two kinds.

- **Soft errors (20–49)** are overcome by an option. 20: `reverse` or
  `info` on metadata with entries this release doesn't know
  (`--proceed-unsafe`). 21: `reverse` on a file modified by something
  else since this tool's last edit (`--proceed-unsafe`). 22: the output
  file already exists (`-f`/`--force`).
- **Hard errors (50 and above)** can't be overcome. 50: invalid command
  line, also when run with no arguments (previously 2, the same as
  `info`'s "180°" result). 51: the input can't be read or the output
  can't be written. 52: not a valid or supported HEIF file. 53:
  `reverse` on a file with no provenance record. 54: made by a later
  release (see above). 55: the record is corrupt, or the original can't
  be restored from it. 56: internal error, including any unexpected
  crash, which used to end in a bare Python traceback and exit code 1.
  57: `rotate`'s output failed its reversibility self-check, so it
  wasn't written.

Every command, with or without `--dry-run`, stops at its first error,
unless the option overcoming each soft error it meets is given, in
which case it stops at the first hard error. If it gets to the end, its
exit code isn't an error one.

Every error is reported on stderr in one line tagged `ERROR Soft NN` or
`ERROR Hard NN` (`NN` = the exit code), so `grep '^ERROR '` lists every
soft error a run met and the hard error it stopped at. A soft error an
option overcame is reported too, unless `-q` is given:

```
ERROR Soft 20 (overridden by --proceed-unsafe): this file was last updated by heic-lossless-rotate 2.1.0 (this is 2.0.0): its metadata has entries this release doesn't know (XNEW). Ignoring them
ERROR Soft 22 (overridden by -f/--force): output file 'photo_restored.heic' already exists - overwriting it
```

The error a run stops at is always reported, even with `-q`. Scripts
that checked for exit code 10, or for `error:` in the output, need
updating. See the README's "Errors and exit codes" section for the full
tables.

## `--proceed-unsafe` replaces `--ignore-tamper-check`

`reverse --ignore-tamper-check` is renamed `--proceed-unsafe`, since it
now covers more than one check, and `info` accepts it too:

| Check | `reverse` | `info` |
|---|---|---|
| File modified by something else since the last edit (checksum mismatch) | overridable | not checked |
| Metadata has entries this release doesn't know | overridable: ignored | overridable: ignored |

Each check it overrides is reported on stderr, unless `-q` is given,
e.g.:

```
ERROR Soft 20 (overridden by --proceed-unsafe): this file was last updated by heic-lossless-rotate 2.1.0 (this is 2.0.0): its metadata has entries this release doesn't know (XNEW). Ignoring them
```

Previously the tamper override was only mentioned on stdout. `reverse`
still always checks that the restored file
matches the original file's checksum, with or without the option. The
old name is no longer accepted, so update any scripts that use it.

## How `rotate` handles older records

Earlier releases converted an old record to the current format on the
next edit, keeping everything that release had written. That meant every
later fix needed extra code to repair files written before it.

Now, when `rotate N` finds a record in an older format, it:

1. runs `reverse` on the file in memory, restoring the original and
   checking it against the original file's checksum stored in the record,
2. works out the rotation the earlier release was asked to add. That is
   the change in the main image's `irot` value, because earlier releases
   always changed it by exactly the requested angle, even when a
   mirrored photo then displayed wrongly,
3. rotates the original by that angle plus N, wrapped to 0°–270° (for
   example 270° + 180° = 90°), exactly as a first edit with 2.0.0
   would, writing a format 3 record.

The result is byte-identical to rotating the original file with 2.0.0
in one go. The usual check that the output can be reversed still runs
before anything is written.

`reverse` reads only the normal final record each earlier release
wrote. It never tries to work around bugs in those releases. Fixing
what an earlier release got wrong is left entirely to step 3, which
uses only the current code.

If the original can't be restored, `rotate` writes nothing. Unless
something else has modified the file since, it names the release that
wrote the record, which checked that it could restore the original,
and the combined angle worked out from the record:

```
ERROR Hard 55: cannot upgrade this file's metadata (format v2): restoring the original file failed: <reason>. This file was last updated by heic-lossless-rotate 1.7.1. Use that release to recover the original, then run `rotate 270` on it with the latest release (90 deg that release added + 180 deg requested now).
```

`reverse` gives the same advice when it can't restore a file that
another release last updated (again, unless something else has
modified the file since), without the `rotate` part. See the README's
`reverse` section for why that release can.

## Truncated `pitm` boxes

A file whose primary-item box (`pitm`) was cut short could make the
tool crash with an internal error, or read past the end of the box.
It is now refused with a clear error message, like any other malformed
box.

## Known limitations

- If a gain map has a rotation property of its own that isn't shared
  with the main image, it isn't rotated. `rotate` prints a warning
  instead. None of the real photos tested are built like this.
- The item-property box must contain exactly one `ipco` and one `ipma`
  box, each with a standard 32-bit size field. A file built any other
  way is refused with a clear error. More than one `ipma` was already
  refused before this release.

## Tests

The suite grew from 68 tests (1.7.1) to 102:

- The synthetic test-file builder can now add a mirror property, either
  before or after the rotation, and a gain map with a `tmap` item. The
  `tmap` item either has its own rotation and size properties or
  shares them with the main image.
- New tests cover:
  - the rotation direction for every mirror axis, property order,
    starting rotation and angle,
  - Exif sync for mirrored files,
  - `tmap` size and rotation, and gain-map alignment, after every
    angle,
  - chains of several edits,
  - repair by `rotate 0` of files rotated the pre-2.0.0 way,
  - format 3 records, including the `OIPM` fallback,
  - `reverse` of format 1 and format 2 records,
  - `rotate` on format 1 and 2 records: the result must match rotating
    the original directly, byte for byte, including when the angles wrap
    past 360°, and `rotate` must refuse with the right advice when the
    original can't be restored,
  - truncated `pitm` boxes,
  - `REQT`, and refusing mirroring, unknown entries and newer formats,
  - `--proceed-unsafe`, exit codes and the `ERROR Soft`/`ERROR Hard`
    tags, including what `-q` hides,
  - the advice to recover the original with the release that last
    updated the file.
- Some real photos from iPhones and Samsung phones (mirrored and not,
  with and without gain maps) were rotated by every angle and in chains.
  Each result was checked for its displayed transform, `tmap` size, gain
  map and Exif value, and checked to `reverse` to the byte-identical
  original. Images rendered with libheif confirmed that 90° now turns
  mirrored photos counter-clockwise.
