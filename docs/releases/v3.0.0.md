# Release 3.0.0 (unreleased): detailed changes

*In preparation: this file grows as changes are made, until the release.*

This release adds flipping: `flip` mirrors an image the same lossless,
reversible way `rotate` turns it, and `rotate --then-flip` does both in
one run. It also makes memory use independent of file size: the tool no
longer loads a photo's image data into memory, only its metadata. It
writes every output file safely, through a temporary file, so the
output may be the input file itself. And it now refuses the few kinds
of file it can't edit safely, instead of producing a damaged one.
The metadata format is unchanged: format 3, as written by 2.0.0.
Rotated files are byte-for-byte what 2.0.0 writes; a flipped file can
only be opened by this release or a later one.

## Flipping

```
heic-rotate flip <horizontal|vertical> <input.heic> [output.heic]
heic-rotate rotate <0|90|180|270> --then-flip <horizontal|vertical> <input.heic> [output.heic]
```

`flip horizontal` swaps left and right, giving a mirror image. `flip
vertical` swaps top and bottom. `h` and `v` are accepted for short.
Like a rotation, a flip only changes metadata, applies to the image as
it is displayed now, and is undone by `reverse` along with everything
else. Flipping the same way twice gives back what you started with.

`rotate <angle> --then-flip <direction>` rotates first and then flips
the result, as a single edit. The order matters: rotating by 90° and
then flipping horizontally differs by half a turn from flipping first
and rotating afterwards, so the option's name says which comes first.
Every orientation can be reached this way.

By default `flip` writes to `<input>_rotated.heic`, like `rotate`.
`--dry-run`, `-f`, `-q` and `--no-exif-sync` work as they do for
`rotate`.

### What `info` reports

`info` reports the total of everything you asked for as a rotation
followed by a flip, the form `rotate --then-flip` takes, so it can be
typed back in:

```
Rotated with heic-lossless-rotate v<version>, provenance format v3.
  heic-lossless-rotate has added: 90 deg, then horizontal flip (the same as 270 deg, then vertical flip)
  file's 'irot' value: 0 deg originally -> 270 deg now
  file's mirroring ('imir'): none originally -> left-right now
```

A total of 180° followed by a horizontal flip is reported as `vertical
flip`. The exit code for a flipped result is the rotation's code plus 4:

| Exit code | `info` result |
|---|---|
| `1` / `2` / `3` / `4` | `90°` / `180°` / `270°` / `0°`, not flipped (unchanged) |
| `5` / `6` / `7` | `90°` / `180°` / `270°`, then a horizontal flip (`6` is a vertical flip alone) |
| `8` | A horizontal flip alone |

So a code above `4` means flipped, and the code's remainder when divided
by 4 is the number of quarter turns.

### How it is stored

The HEIF mirror property, `imir`, can't say "not mirrored", so a flip
adds or removes it rather than changing its value. An image that isn't
mirrored gets an `imir` as the last of its properties (an identical box
already in the file is used if there is one). An image that is mirrored
already, such as an iPhone front-camera shot, has its `imir` taken off;
the box stays in the file, unused. The `irot` value then makes up
whatever rotation is still needed, and an `irot` is added before the
`imir` if the image has none. So the result is always a rotation
followed by a mirror, the order iPhones write. A flip on its own leaves
the `irot` value of an unmirrored image as it was.

A photo's thumbnail, auxiliary images (such as depth maps) and HDR gain
map normally carry the very same rotation and mirror properties as the
main image. Those that do get the same changes. In every iPhone and
Samsung photo tested, all of them do. The gain map's tone-mapped
(`tmap`) image keeps its own rotation and gets the new displayed size,
as for a rotation.

The legacy Exif Orientation tag is updated too, with its mirrored
values (2, 4, 5 and 7) when the result is mirrored.

### Compatibility

Flipping needed no new metadata format: format 3 has recorded "what was
requested" with room for a flip since 2.0.0. But earlier releases can't
flip, and refuse a flipped file: 2.0.0 with hard error `54` ("it was
mirrored, which this release doesn't support yet"), in `rotate`,
`reverse` and `info` alike. Use this release or a later one on such a
file.

A file rotated by an older release (formats 1 and 2) and then flipped
is handled like a rotation of it: the original is restored, then given
the earlier rotation and the flip in one edit.

## Memory use no longer grows with file size

Earlier releases read the whole file into memory and, since 1.7.1,
needed about twice the file size at peak. Now only the file's metadata
is read into memory: the `meta` box and the tool's own record, usually
tens of kilobytes. The image data is copied from the input file to the
output file in chunks of 1 MiB, and the checksums the tool records and
verifies are computed over those chunks as they pass.

`rotate`'s check that its output can be reversed works the same way: it
reverses the output before any of it is written, without holding either
version of the file. `info` reads only the metadata, so it takes about
the same time for a file of any size.

On a 300 MB test file, `rotate` used 636 MB of memory with 2.0.0 and
about 19 MB now, most of which is Python itself, and ran in about half
the time. The output is byte-for-byte the same as 2.0.0's.

## Output is written through a temporary file

Earlier releases wrote the output file directly. If that was
interrupted while overwriting an existing file with `-f`, the file was
left half-written. Now `rotate` and `reverse` write a temporary file
next to the output file and rename it into place only once it is
complete and the input file is closed. So:

- an interrupted run never leaves a half-written output file. The
  temporary file is removed too, unless the process is killed outright,
  which can leave a hidden `.<name>.….tmp` file next to the output;
- the output file may be the input file itself (with `-f`), even
  though the input is now read while the output is written;
- an existing output file keeps its permissions, and an output path
  that is a symbolic link stays one, pointing at the new file.

Two consequences of replacing the file rather than writing into it: if
the output file has other hard links, they keep the old contents, and
the output file's directory must be writable.

If the input file changes while the tool is working on it, nothing is
written, and the tool exits with error `51`.

## Files the tool can't edit safely are refused

When `rotate` changes the size of the `meta` box, which it always does
on a file's first rotation since that adds its record, everything after
`meta` in the file moves. The tool updates the image locations recorded
in `meta` itself (`iloc`) to match, but nothing else. Earlier releases
didn't check for anything else, so a file that also referred to the
moved data some other way was left pointing at the wrong place. Such a
file is now refused, with error `52`, and nothing is written, when the
edit would move data and:

- the file has a top-level box that may refer to data by its position
  in the file: a `moov` box (as in image sequences), a second `meta`
  box, or any top-level box other than `ftyp`, `mdat`, `free`, `skip`,
  `wide` and Samsung's `sefd` trailer; or
- an image's data is located through a data reference (`dref`), which
  may point into another file, and its location would have to change.

Files with `meta` at the end are never refused for this, since nothing
moves. All the real photos tested, from iPhones and Samsung phones, are
unaffected: they contain only the boxes listed above, and locate their
images in the file itself. Samsung's `sefd` trailer was checked
specifically: it locates its contents relative to itself, so it can
move.

Also refused now, with error `52`: a file whose embedded Exif data is
stored inside the `meta` box itself, rather than with the image data.
`reverse` could never restore the Exif Orientation value there, so
`rotate` already refused to write such a file, but only after its
reversibility self-check failed (error `57`).

## Exif data located through a data reference is no longer synced

The tool keeps the legacy Exif Orientation tag in sync with the
rotation when the Exif data is stored at a position in the file. If
the Exif data is located through a data reference (`dref`), that
position may belong to another file, and earlier releases could
overwrite two bytes at that position in this one. The tool now leaves
such Exif data alone, as it already did for Exif data stored in other
ways it doesn't handle.

## Smaller fixes

- A box whose 64-bit size field gave a size smaller than the box's own
  header could make the tool hang. Any box declaring a size smaller
  than its header is now refused as malformed (error `52`).
- `reverse` on a record missing a required entry stopped with an
  internal error (`56`). It now reports a corrupt record (`55`).

## Exit codes

`info` has four new result codes, `5` to `8`, for flipped files (see
[What `info` reports](#what-info-reports)). No error codes were added
or changed. Some conditions now map to a different code than before, as
described above:

| Condition | Before | Now |
|---|---|---|
| Input file changed while being processed | — (not detected) | `51` |
| Box declaring a size smaller than its header | hang | `52` |
| Unsupported data that would move (see above) | not detected | `52` |
| Exif data stored inside `meta` | `57` | `52` |
| Record missing a required entry | `56` | `55` |

Offsets quoted in error messages about malformed boxes inside `meta`
are now counted from the start of `meta`, not of the file.

## Known limitations

New in this release, see
[Files the tool can't edit safely are refused](#files-the-tool-cant-edit-safely-are-refused):

- A file is refused when an edit would move data that a top-level box
  other than `ftyp`, `mdat`, `free`, `skip`, `wide` and `sefd` may
  refer to, or an image located through a data reference whose location
  would have to change. The check doesn't look inside those boxes, so it
  also refuses some files that would have been fine, for example one
  whose `moov` box only refers to data before `meta`.
- A file whose Exif data is stored inside the `meta` box is refused.

For flipping:

- A thumbnail, auxiliary image or gain map that doesn't have the same
  rotation and mirror properties as the main image is left as it is.
  `flip` prints a warning, and a viewer that shows that image may show
  the old orientation. This includes the thumbnail of a photo that had
  no rotation property until `rotate` added one: `rotate` gives the new
  property to the main image and the gain map only.

## Tests

The suite grew from 103 tests (2.0.0) to 145:

- Flipping: every request (4 rotations, each with and without a flip)
  on every starting layout, checking the display, the Exif Orientation,
  what `info` reports, and that `reverse` gets back the original; every
  pair of requests, checking that two edits equal the one combined
  edit; thumbnails and gain maps following the main image; the `flip`
  command and `rotate --then-flip`; replay of older records.

- Results computed from a file on disk must match results computed in
  memory, byte for byte, for chunk sizes from 1 byte up, so that a
  chunk boundary falls on and inside every edit.
- No read of the file may be larger than a chunk, `info` must read only
  the metadata, and peak memory across `rotate` and `reverse` runs must
  stay far below the file size.
- Rotating and reversing a file onto itself, including a file large
  enough to need several chunks, repeatedly and in both box layouts;
  no temporary file may be left behind, whether the run succeeds or
  fails; permissions and symbolic links are kept.
- The new refusals, and the cases that must keep working: `free`,
  `skip` and `sefd` boxes after `meta`, and any box at all when `meta`
  is last in the file.
- Malformed boxes, a file that shrinks while being read, a record
  missing a required entry, and a record box that something else moved
  away from `meta`.

Beyond the suite, 2.0.0 and the new code were compared on about 418,000
cases built from 360 synthetic files: rotations, chains of rotations,
`reverse`, `info`, and copies of every result with a byte changed.
Every output was identical; the only differences were the error changes
described above. Real photos from iPhones and Samsung phones were
rotated and reversed and the results reviewed.

For flipping, rotation-only edits were compared with the previous code
on 432 synthetic files and the real photos (about 9,700 comparisons,
all byte-identical). The real photos were also flipped and decoded with
libheif, and each result's pixels compared with the original's: every
one was exactly the requested flip.
